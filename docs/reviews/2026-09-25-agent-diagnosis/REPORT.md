## 4. 主要问题与优先级

P1 表示应进入下一轮有限修复；P2 表示随后补齐。未发现足以认定需要立即停止整个工作台的 P0 证据。`VALIDATE` 表示下次实现前后需要定向复现，不能按现网已发生事故描述。

### D01 · P1：原动作和前提的保真检查弱于执行检查

**证据层级：历史真实样本 + 本轮正式 UI + 代码确认。**

`development-session.mjs:88–100` 核对覆盖项数量、原预期文本、行号范围和自测结果；`report.mjs:129–131` 的 complete 核对步骤标记与顺序。`check_fidelity` 是可选工具（session:56–58），有限规则也不覆盖一般操作前提。模型写了全部步骤并报告通过，仍可能额外操作或漏断言。

建议在提交时自动输出绑定候选包哈希的要求核查材料：逐项保留原前置、动作、预期、对应代码和运行观测；已有明确规则能识别的问题必须显式标不完整；无法判断的语义保留待核查。先覆盖 KC-01/07/10/12/23，不做通用自然语言自动裁判。继续保留人工批准边界。

### D02 · P1：恢复任务“先执行原稿”可被另一写入入口绕过

**证据层级：生产函数探针已复现，使用替身，未执行业务。**

`development-session.mjs:49` 只限制 `write_draft`；`development-tool-guard.mjs:20` 允许 native write/edit；session:111–116 对当前文件直接打包。探针中 write_draft 正确拒绝，但同一允许范围的 native edit 后，首次 self_test 取到的是修改后的哈希，原稿没有进入验证器。验证器随后按探针设计返回 `EXECUTOR_ERROR`，这不是一次模型自测成功。

建议在首次 recovery self_test 强制比较授权完整种子包哈希，覆盖入口及 helper；或在原稿执行前统一拦截所有写入入口。不要只强化提示词。新稿、原稿和修订稿证据分别保留。

### D03 · P1：停止可覆盖终态，留下“停止中但已无活动任务”

**证据层级：代码竞态 + 生产停止函数在注入收口窗口中已复现。**

`candidate-trials.mjs:150` 排队保存终态，active 直到 :110 的 finally 才清除；:155–157 仅检查 active 并无条件写 STOPPING。探针把已落盘 FINISHED 且 active 尚未清除的窗口注入生产停止函数，结果变为 STOPPING，active 清除后不会再有执行器推进它。尚未在真实并发浏览器运行中复现这个时间窗口。

建议收口阶段明确不可倒退；停止写入在持久化 updater 中检查非终态，终态请求幂等返回。用可控写入栅栏覆盖“结果保存前/中/后”三个停止点。

### D04 · P1 / VALIDATE：后台存储错误可能逃逸，异常收口方式不统一

**证据层级：代码确认，未做磁盘故障注入。**

`candidate-trials.mjs:110–111` 只保存 Promise，:147–150 的异常分支仍依赖原读写；`script-operations.mjs:81、106` 同类。持续磁盘满/权限/占用异常可能令后台 Promise 再次拒绝。`build/manager.mjs:926` 已有 completion.catch → 存储故障隔离路径，可复用这一模式。

建议统一捕获后台拒绝、进入 degraded 并停止接纳新任务；即便落盘失败也保留可查看的内存故障状态。禁止吞错伪造终态。验收注入开始、结果、终态三处写入失败，检查服务存活、拒绝新任务和恢复后的可解释状态。

### D05 · P1：默认测试与启动入口尚未服从唯一工作台规则

**证据层级：代码确认；本轮未执行冲突脚本。**

`workbench/package.json:18` 的通配符单测包括 `build-api.test.mjs:43–44`、`development-production.test.mjs:59–60`、`candidate-trials.test.mjs:84` 等另起随机端口工作台的测试。`build-real.integration.mjs` 有独立服务及真实模型路径，`real-workbench.integration.mjs:10` 默认仍指向 4210。根 README:31 和根 package.json 仍引导旧 4179 产品。

建议分开纯函数/协调器检查、只连现有 4322 的正式功能验收、显式有界模型验收三个命令；把 API 单元测试改为 handler/store 层调用，避免另建工作台。统一根入口说明，不删除历史证据或为了本次诊断迁移旧实现。

### D06 · P2 / VALIDATE：取消、互斥和关机尚未覆盖全部阶段

**证据层级：代码确认，未在正式服务注入。**

- 初始化：`adapter.mjs:17–26` 的两个本地子进程没有传 signal，取消可能仍等待 60 秒/180 秒本地超时；后续主 Harness 的取消机制不能弥补这段等待。
- 跨执行器：`app.mjs:516` 与 `index.mjs:81` 只看另一管理器 active，遗漏各自 starting 的异步准备窗口。批准资产入口仍存在，虽然当前常用候选路径有额外协调保护。
- 关机：`index.mjs:99–114` 在后段才 close server，也未显式停止/等待 WorkbenchRunManager；等待收口期间仍可能接新工作。

建议复用一个同步取得的执行权覆盖准备、执行、收口；初始化全程传取消信号；关机先拒绝新写请求，再结束本进程拥有的全部执行器。不要以结束未知进程替代生命周期管理。

### D07 · P2：失败归因与独立复核还不够完整

**证据层级：代码 + 历史运行记录。**

`development-task.mjs:135` 对 non-ready 提交直接返回；历史 6 个失败任务没有独立执行。business_difference / needs_analysis / environment_blocked / budget_exhausted 均进入 CANDIDATE_VALIDATION_FAILED，虽然原 outcome 仍保存，任务级统计不易区分。独立正常验证发生在 Harness 会话结束以后，也没有同会话回流修复。

建议保留生命周期状态，增加稳定 reason/category；区分 Agent 缺陷、业务差异、环境、输入冲突和预算。对可执行的失败候选提供有界零模型独立复核，输入冲突先待确认，不盲目再跑。不因最终失败自动开新任务重置预算；独立验收发现的问题先保留为后续有依据的修订输入。

### D08 · P2：修复反馈与能力说明导致可避免的空转

**证据层级：代码 + 历史工具错误分类。**

`development-feedback.mjs:11` 对预算耗尽等错误仍建议 write_draft/self_test，而 session:52、110 已禁止这些动作。工具政策还拒绝部分合理只读表达式；139 次策略拒绝中同时存在应拒绝操作，不能整体放开。

建议按错误码返回当时真正可执行的下一步；识别“相同包哈希、相同错误、没有新证据”的重复尝试并停止。只从真实错误中挑少量高频合理读取能力补支持，并保留直接改 DOM、存储访问和任意代码执行限制。供应商 usage 能取则记录，取不到保持未知。

### D09 · P2 / VALIDATE：认证并发与真实登录场景需要单独验收

**证据层级：静态竞态 + 本轮正式页面边界。**

`auth/session.mjs:76–100` 在异步启动浏览器和导航后才放入 sessions Map；同 scope 并发 open 可能创建两个浏览器，后者覆盖前者。建议对 project/environment/role 合并打开中的 Promise，并让 clear/close 管住准备中的对象。

当前环境页展示已绑定的 AUTH-TC-001 合成能力，本轮未登录、未采集凭据。不能沿用旧记忆中的“任务尚未绑定”作现状，也不能升级为通用业务登录已通过。真实登录过期、清除会话时中止、再次登录后的复跑，仍需在明确授权环境独立验收。见 [本轮登录页证据](auth-live-dom.txt)。

### D10 · P2：加载版本、用户旅程与当前证据缺少统一基线

**证据层级：当前进程/健康响应/文件时间 + 近期报告。**

健康接口有 service_instance_id，缺少已加载代码及有效配置摘要。当前 script-operations.mjs 修改时间 20:50:04 晚于进程 20:46:30，不能证明磁盘代码就是已加载后端。本轮不重启验证，也不把旧报告里的“重载受阻”照搬为当前事实。

近期 v9 报告承认先前准备好的授权/脚本遮蔽了额度耗尽、多脚本选择、本机目标未准备三种普通状态。当前 UI 已展示新的生成/复跑说明，但不能据此认定整个 v9 流程已验收。旧 KC-10 明确缺逐步实际值和可靠时标；保留这些历史缺项是正确行为。

## 5. 有界优化计划

以下为建议实施顺序，不代表本轮已经授权执行模型任务或承诺工期。负责人按职责分工：实现 Agent 负责修复；独立验证 Agent 复验；主管核对证据；业务原义及候选批准由用户决定。现有任务结束后再安排影响服务的工作。

| 顺序 | 有限工作包 | 具体交付 | 验收与停止条件 | 依赖 |
|---|---|---|---|---|
| O1 | 固定当前基线与测试入口 | 统一 4322 文档/命令；纯工程测试清单；已加载代码/配置指纹 | 默认工程检查不另起工作台、不调用模型；正式验收只能连接4322；同一运行能追溯确切构建 | 无；先执行 |
| O2 | 修复恢复与运行收口 | 完整种子包校验、终态不倒退、存储异常捕获；取消/互斥/关机必要修补 | native/helper 修改不能跳过原样执行；终态停止幂等；故障注入不无解释退出；并发仅一个执行者；空闲后同4322有限复验 | O1 |
| O3 | 原要求保真与失败分层 | 绑定包哈希的有限核查材料；动作/前提漂移提示；失败分类及有界独立复核 | KC-01/07/10不能再把改前提当原路径成功；KC-12保留待确认；KC-23覆盖缺项被指出；业务差异和输入冲突不被修成绿色 | O2；复用当前样本 |
| O4 | 减少无效修复成本 | 错误码对应下一步；同包同错无新证据停止；少量合理只读能力支持；成本字段 | 耗尽后不再建议不可执行动作；已确认工具误拒绝消除且禁用行为仍拒绝；预算累计，不新增隐式重试 | O3；先做局部对照 |
| O5 | 正常用户旅程和有限真实试点 | 普通入口完整链路检查；登录并发修补/恢复验证；一份分层验收报告 | 同4322完成生成确认/取消→版本选择→复跑→证据→下载→刷新读回；每个未完成项有原因；有真实资料时仅一个模块最多3条，否则停在缺少输入 | O1–O4及用户提供的业务事实/明确模型预算 |

**推荐下一轮只承诺 O1 + O2。** 这两项可先完成大部分零模型工程验证，再用正式工作台有限验收收口。达到上述停止条件后结束该轮，不顺带扩多模型、长期记忆或分布式执行。O3 涉及新验收语义时再按项目规则复用/建立直接相关 REQ，不在诊断阶段把建议写成已确认业务规则。

O3/O4 的效果验证先固定少量代表例：前提漂移、真实业务差异、字段语义修复、工具读取阻塞各有一个样例。固定用例、页面、模型配置与资源上限；先比较逐义务结果及错误类别，不追求全绿。只有这组达到验收，再扩到固定24条完整回归，不跨构建拼成绩。

## 6. 后续应该看哪些指标

1. 原要求核查完整的候选数 / 本次冻结用例数；输入冲突、业务差异、阻塞分别列出。
