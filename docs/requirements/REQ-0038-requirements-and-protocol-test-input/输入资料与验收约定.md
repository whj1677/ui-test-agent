## 1. 给产品经理和测试工程师的提交要求

### A. 从 pm-req 产出生成测试用例

| 资料 | 是否必须 | 怎么提供 |
| --- | --- | --- |
| 本轮需求资料 | 必须 | **主输入为 PRD、MRD 文档**，支持 Word/Markdown；两份都有就一起提供，只有一份也可先分析。能否形成完整用例按内容判断，不强制凑齐两份。pm-req交接ZIP是可选增强材料。不要只给文件名或空模板。 |
| 本次测试范围 | 必须 | 项目、模块以及本期要测的功能。可直接选择导入资料中的范围；若是全部本期交付项，选“本期全部”即可，不必重写需求。 |
| 正常与异常行为的判定依据 | 相关用例形成确定预期前必须 | 需求中的业务规则、验收条件、角色权限、状态变化、边界和异常处理；资料已有的无需重复填写。缺失或冲突的部分进入待确认清单。 |
| 原型、页面截图 | 可选 | 有就提供，并注明属于哪个页面/流程、是当前系统还是本期设计。没有截图也可以开始。 |
| 通讯协议 | 可一并导入；后端自动化绑定前须具备所需定义 | 接口/命令、请求响应、字段与约束，可来自独立协议或已有文档附件；不凭上传一个文件就判资料完整。缺少时标明受影响的后端技术步骤。 |
| 文档确认与模型使用范围 | 必须确认一次 | 导入页确认使用哪个版本、需求是已确认还是评审稿，以及文字和图片是否允许发送给本机已配置的模型服务。信息已有则自动读取供核对，不要求人工填写技术标识。Word本身不因没有机器清单而被拒绝。 |

PRD与MRD共同作为事实源，按实际内容识别功能、规则、范围和验收要求，不仅凭文档名称规定优先级。重复要求合并并保留双向来源；冲突要求列出差异，不能静默以PRD或MRD覆盖另一份。两份文档都有也不等于规则一定完整。

进入资料页前先在项目列表选定项目；页面持续显示当前项目 ID 和名称。资料、前后端用例、协议绑定、脚本/执行批次和报告归该项目。统计、筛选和批量动作默认限当前项目；切换项目清空选中集及旧筛选结果，不隐式合并不同项目的用例、绑定、执行或证据。资料未来可以显式复用，但不默认共享；项目复制与跨项目报表本轮不做。

**没有截图时**：依据已有文字生成业务功能用例，给出前置条件、测试数据要求、操作和预期、来源引用；文字已明确的页面操作可以保留。不能杜撰按钮名称、页面布局、颜色、提示文案或定位器。无法确定的界面细节标记“待页面绑定”，不因此阻止无关功能用例的设计。

**只有截图时**：当前只保存图片并明确显示“未分析”，不能单独生成候选。后续接入识图后也只允许提取可见事实，不能据此推导完整业务规则、权限、后端校验、错误码或不可见分支；文字与图片冲突须保留双方依据供负责人确认。

输出明确分为两组：前端（UI）测试用例与后端功能测试用例。每条包含类型、编号、模块、前置条件、输入数据、逐步动作/预期、来源位置、确认状态和自动化准备状态。分别审阅确认、入库；默认输出前端与后端两份 Excel，JSON 也按类型分别导出。共同需求保留关联，各自验证目标不同，不能复制换标签。同步给出需求覆盖、待确认问题及排除范围；未执行的结果保持“未执行”。拆分发生在本工程从需求生成测试用例的阶段，不要求修改 pm-req 的 PRD/MRD 导出。

### B. 后端用例所需的协议补充资料

以下资料可与 PRD/MRD 同批导入，也可在后续补齐。两端均以已确认测试用例进入自动化；协议不是绕过人工用例、直接生成并执行后端测试的入口。表格中只需补已有资料缺失的部分。

| 资料 | 设计用例所需内容 | 缺少时怎么处理 |
| --- | --- | --- |
| 协议文档与本轮范围 | 文档版本、被测模块、要测的接口/命令/消息；传输方式及连接说明 | 能识别的部分先设计；执行适配类型不明时保持待绑定 |
| 报文与交互约定 | 请求/响应或命令/反馈格式，字段含义、类型、单位、有效范围、必填项、正常样例、错误返回，身份认证方式；异步协议还需关联方式、触发和完成条件 | 有来源的字段可设计格式/边界候选；未知值不编默认值。协议不涉及的项目标“不适用” |
| 功能判定依据 | 每个操作应产生什么结果：返回内容、业务状态变化、权限、异常分支；存在超时、重试、幂等或状态机要求时给出其明确规则 | 只有通信格式就只能形成协议格式检查候选；不能声称已设计完整后端功能用例 |

**通讯协议不等于完整的业务需求。** 协议回答“怎样交互”，功能测试还需要知道“执行后应有什么变化、怎样判断正确”。已有 PRD/MRD 和验收条件可以直接作为这部分依据，无需另外重写。

PRD/MRD若已规定“重复编号必须拒绝”，可先形成相应后端业务用例；没有协议时不能补造接口地址、字段名和响应码。用户已同意这类有依据的业务用例可设计、确认和导出，同时标记“待协议绑定、不可自动化”。有协议但业务结果不明或与需求冲突的条目仍须澄清。

后补协议时，在协议与绑定页沿用已确认的后端用例编号和版本，逐步核对动作、预期、字段、单位、约束和可观察结果。纯技术映射只增加 binding 版本，不改原用例内容和旧导出；协议提出新的业务规则或与原预期冲突时另建待核对的候选用例版本。部分步骤已映射不代表整条用例可运行。绑定完整仍需核对执行器、环境、测试数据和脚本；协议、用例或绑定版本变化后重新检查适用性。

### C. 真正连接后端执行前再补交

| 资料 | 必需内容 |
| --- | --- |
| 非生产测试目标 | 测试环境地址/端口或设备/总线接入方式、部署版本、允许访问的范围；执行前核对实际目标 |
| 访问条件 | 账号角色、登录/认证方式、凭据如何在本机配置；密码、Cookie、Token、密钥不要写入需求文件或聊天 |
| 数据准备与结果观测 | 可用测试数据、准备方式、怎样读回状态变化；异步消息的关联标识和等待条件；无现成数据时由负责人确定可创建的数据范围 |
| 操作与清理边界 | 允许执行哪些读写操作，哪些禁止；写入数据的唯一标识、清理/恢复方式和失败后的处理人。没有授权的破坏性操作不执行 |

此阶段才要求环境和访问条件。没有测试环境仍能设计用例，但不生成“执行通过”的结论。协议未定义的异常值、等待时间或清理动作不由模型自定。

## 3. pm-req 实际对接事实与设计边界

本轮只读核对了 pm-req 的 app/exports.py、app/requirements.py 和下载入口。PRD/MRD可独立下载Word、Markdown或文档ZIP，可能带“评审稿”或指定版本确认说明；**这两类文档是产品主入口**。正文、表格和图片的内容读取与确认状态分别核对，不因只交Word而要求另造机器交换包。

可选的正式 handoff ZIP 当前 manifest.schema_version 为 1.1，含 baseline_id、baseline_hash、confirmation_id 及 artifacts 逐文件摘要；requirements-exchange.json 使用 exchange_version=requirements-exchange-1，保留需求 namespace/id/version、内容哈希、来源与关联。还提供 requirements.md、acceptance_criteria.md、open_questions.md、traceability.json、ui_spec.json、prototype.html，以及已生成的 PRD/MRD 内容。原始截图未作为固定包条目，应允许单独添加。

关键差异：正式交接文字的 delivery_items 会按 selected、to_be 和本期 scope 筛选；exchange() 当前遍历全部被跟踪条目。**导入器不能把交换 JSON 的每条需求都当作本期交付项。** 首批实现需交叉核对正式交付文字/追溯条目与交换条目身份；无法唯一确定时让用户选择范围。后续可为上游增加明确的 delivered_item_refs，但本轮不修改 pm-req，也不静默读取其日常数据库代替导出。

manifest 校验只能证明包内一致性，不是产品经理身份签名或“这是最新版本”的证明。导入页仍要确认本次采用范围和版本。无论Word、Markdown还是交换JSON，确认信息无法自动核实时交由用户核对；来源格式不决定用例成熟度，需求确认也不替代测试用例人工确认。

压缩包导入需检查路径穿越、重复条目、容量及展开上限、清单缺项和哈希差异；HTML 原型作为参考资料读取，不自动执行脚本或外链。附件内容作为事实源，不作为对 Agent 的指令。正文、表格、图片分别记录成功、部分或未读取，不能把上传成功当作理解完成。

## 4. 有限实施顺序与验收

1. **需求输入和用例设计**：先接 PRD/MRD 文档，建立来源、范围和版本；无截图能够设计有文字依据的功能用例，缺规则产待确认项。首批验收覆盖只有PRD、只有MRD、两份互补/重复/冲突、有图/无图、Word评审稿和版本变化。可选ZIP入口另验清单篡改、范围外条目，不作为主文档入口的前置条件。
2. **用例确认与复用**：UI/后端候选分别展示、人工修改确认、导出和入库；来源版本改变时标记受影响用例需要复核，旧用例和结果保留。没有确认的候选不能自动获得执行资格。
3. **一种协议的后端执行闭环**：拿到首份实际协议后，只实现该协议对应的适配器。HTTP/HTTPS与设备/消息协议是待选择分支，不默认把所有通讯协议解释成HTTP，也不同时建设所有执行器。

后端结果必须区分：连接/认证失败、协议格式失败、业务断言失败、超时、未执行及清理失败。成功不能仅以HTTP 200、收到响应或字段存在判断；要按原用例核对状态和值。报告保留脱敏请求/响应、关联标识、原预期、实际值、时间信息和清理结果。

执行页保留可分页、筛选的多用例列表，摘要统计与当前批次/筛选范围一致。每条直接显示状态、失败摘要、原预期/实际观察简述和证据/详情入口；失败、受阻、未执行分开，可只看异常。相同报错分组只是“候选同因/待核对”，不是已证实根因。可选中失败集合批量反馈修订或复跑，仍保存逐项结果和历史，不静默跳过；原脚本复跑不调用模型，并先核对版本与执行条件。

首批后端验收至少包括：正常读取、明确业务错误、权限拒绝、业务状态变化、文档定义的异步或超时行为、失败后的清理（不适用项注明原因）；以模拟目标作执行器工程反例，再在获准的非生产目标验证。工程模拟不冒充真实系统验收。

首轮停止记录：需求到两组用例、确认导出、协议后补与冲突修订的合成主路径及历史执行列表已检查；该轮4次文档模型请求已用完，包含2次格式失败。此记录保留为当时状态。

2026-09-26续轮：已接入单独授权的PNG/JPEG模型输入，并建立合成namespace HTTP/JSON首批适配器、真实台账目标与共享执行批次。实际覆盖和限制以 `workbench/qa/20260926-req0038-completion/REPORT.md` 为准；不支持任意HTTP接口、真实令牌鉴权或设备/消息协议。普通业务接入仍需提交上面C节资料，经独立适配和授权验证后才能执行。文档内嵌图、客户试点与完整发布验收仍不能计为已验证。
