## 建议一：导出全项目最新测试结果

推荐按钮文案为“导出全项目最新测试结果”，避免把用例版本、脚本版本和运行次数混为“最新版本”。保留原单次执行、批次导出。

建议规则：

1. 导出前固定项目用例清单、各用例当前版本、报告截止时间及被测范围。前端与后端在同一报告中分组展示，项目用例不能因没有成功结果而从分母消失。
2. 默认“全项目（每条用例最新一次）”先为每个当前用例版本选择最近一次正式执行，再按这些结果实际的被测系统、角色与软件版本分组；全项目每条用例只出现一次，未测用例单列。明确标注各结果可能来自不同时间/配置，不代表同版本一轮全量验证。用户可改为指定被测范围，限定同配置/角色/软件版本取最新；另保留所有历史范围展开模式供核对。依据服务端执行开始时间排序，结束时间与run_id作为稳定次序补充；不能倒查最近一次成功。
3. 失败、取消、中断、阻塞、证据不完整均保留真实状态；没有匹配记录标“未执行”。当前用例版本已经修改但未测，标“当前版本未执行”，旧版本成绩仅供历史查看。只有新脚本尚未运行时，不把脚本生成/自测当作新的正式结果。
4. 截止时仍在运行的用例明确标“执行中”；此前终态结果可作附注，不能当作本轮最终结论。并发完成不改变已冻结的导出选择。
5. 多个被测配置、角色或软件版本不能静默拼成一次全量验证：默认每个当前用例取最新记录后按实际范围分组；需要同范围比较时可显式选定一个范围，标明各组覆盖、缺测与时间跨度。旧记录的范围/版本缺失显示“未记录”，不自动认定等同当前范围。
6. 每个用例保留所选run_id、用例/脚本版本、执行时间、结果、步骤、截图/录像及复测次数。该条目的步骤和媒体必须属于同一次执行；旧失败可折叠查看，不覆盖。导出前预览“通过/失败/未执行/执行中/证据不完整”等实际分类，生成固定快照。

例：A第1次通过、B第1次失败第3次通过、C第1次通过，则摘要选A第1次、B第3次、C第1次；若B第4次失败，再导出必须显示第4次失败。不得以“最新通过”取代最新结果。

以上方案已获用户“可以，按这个推进吧”确认，作为本轮实现与验收依据；实际实现状态与结果另记，不把设计批准当作功能已实现。

## 建议二：将“环境”解释为被测系统配置

“环境”表示脚本要访问的被测网站/接口及允许测试的范围；部分已接入配置还绑定登录方式和角色。创建配置是保存一个测试目标的连接与约束，不是部署一套服务器，也不是安装Node、浏览器或DeepSeek。

项目组织业务资料、用例和报告；被测配置决定对哪里执行；软件版本说明测的是哪个构建；登录会话表示当前是否登录。重新登录、重跑用例通常不需要新增配置。首次接入另一个地址、区分测试/预发布站点或改变允许路径范围时才需要新增配置；原配置不删除，保留历史追溯。

当前自助登记入口仅支持无需登录的非生产HTTP(S)目标；已接入的需登录合成库存台走另外的认证配置。不能因为现有库存台可以人工登录，就宣称自助登记支持任意SSO或接口鉴权。

建议界面：

- 将普通操作中的“环境”改为“被测系统”；项目设置中管理“被测系统配置”。单一配置默认使用，始终显示名称和实际地址，提供“切换/查看配置”；多个配置时再显式选择。
- 列表显示名称、前端/接口用途、实际地址、是否需要登录、来源、登记时间、登记人文本和当前可用状态。自动准备本机页面、项目界面登记、启动配置接入等来源按真实记录标记；旧项缺少来源或创建人时显示“历史配置，来源/登记人未记录”，不猜测。
- 不建议直接删除底层目标选择能力，否则不同站点容易混测。用户若后续仍倾向移除选择器，可仅隐藏单一配置场景的下拉框，继续保留可见目标及后台绑定。
- 现有自助登记只有新增，没有编辑/删除入口。修改URL或路径范围会产生新的环境身份，旧候选执行授权不转移；任何未来改名/停用功能须保持历史记录和引用可读。

核对人字段为本机操作者自填文本，不是已认证的账号身份，因此不能可靠声称某个历史项一定“由你创建”。

### 正式界面验证后的设计收敛
